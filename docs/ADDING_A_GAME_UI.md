# 新游戏的 Web 界面接入

适用于 PC 2.1.1 的 Electron / React 界面。先完成原生游戏和数据源模块，并提供真实能力、工作区与展示契约，再开放可运行的 UI。PUBG 保留既有页面，CS2 有独立概览、显示设置、原理及配置模式，仅声明 ESP 和 algorithm-details；GTA5 仍未接入。

## 1. 先确认数据与语义

同名参数不能默认同义。新增游戏先写清坐标/角度/距离单位、相机视角、实体身份、骨点语义、输入灵敏度、武器/弹道模型以及各数据组当前性的来源。没有的能力明确缺失；不能借用 PUBG 的灵敏度、骨点、归零距离或资料填空。

已接入 Reader 的正式协议保持冻结；PUBG 的禁改要求不变，CS2 v1 已由用户审阅后配对接入，不临时增补未核验字段。没有正式数据适配时保持 unavailable，capabilities 为空，不向用户提供可运行配置。

## 2. 增加共享类型

位置：packages/shared/src/models/workspaces.ts、packages/shared/src/games/<game-id>/。

- 游戏 ID 是稳定枚举；显示名称允许翻译，不能用显示名称反推 ID。
- 当前 UI 能力 ID 为 esp、aim、input-calibration、algorithm-details。确实需要新能力时显式扩展枚举、原生映射、页面和回归，不传任意 JSON 或代码。
- 为新游戏定义独立 Zod 设置/状态 schema，明确 optional、null 与真实 0 的语义。不要给现有 PUBG schema 填入大量跨游戏可选字段。
- applicationSettingsSchema 是真正共享的 DPI / 显卡设置。旧 settingsSchema/values 是 PUBG 兼容展示投影，不作为新游戏的持久化设计模板。
- 游戏业务命令和事件应明确类型与工作区作用域；扩展 shared 的作用域规则后，同步 Electron 与 C++ 验证。
- 现有接口保持 strict 校验，地址/大整数使用既有字符串约定。

游戏的静态能力只说明存在实现，不能代替数据、会话或硬件当前就绪判断。

## 3. 实现游戏 UI 模块

位置：apps/ui/src/games/<game-id>/。参考现有 games/contracts.ts 与 games/pubg/，实现 GameUiModule：

| 入口 | 职责 |
| --- | --- |
| id | 稳定游戏 ID |
| SourcePanel | READER 页中本游戏真实数据源连接与订阅 |
| DataPanel | 数据看板中本游戏的人物、物品、角度及运行遥测 |
| AimSettings | 本游戏有效的目标/跟随/弹道参数视图 |
| settings | 设置分类、说明、可选能力条件与专属面板 |

把已实现模块加入 games/registry.ts 的编译时注册。不得根据工作区文件中的路径任意加载脚本、组件或 Node 模块。目录元数据出现某个游戏不表示其 UI 或原生实现已经存在。

共用 Reader、DataDashboard、Esp、Aimbot、GameSettings 页面保持组合职责。能共享的基础控件、设备比例速度、运行摘要和几何展示继续复用；只有真正不同的来源、参数、校准与说明放入专属模块。不要为每款游戏复制一整套外壳、全局设置或日志页，也不要在公共页面堆积 gameId 条件分支。

游戏导航及设置按能力显示。缺失骨架、观战、弹道等数据时如实标注不可用，不能展示为有效零，也不能让隐藏设置在后台继续参与计算。

## 4. 保持工作区和设备隔离

每个已接入游戏只有一份配置，由原生自动初始化，UI 只发出 read/switch；侧栏仅显示正式游戏名称，不提供创建、重命名或管理页面。切换事务的停止、采集取消、Reader 退订、旧场景清除、保存和新状态发布均由原生/宿主协调。

所有游戏命令使用开始时的 workspaceId + gameId + epoch。事件必须有同一上下文；缺少上下文的正式游戏事件和旧代次回调均拒绝。全局 application 快照不带游戏上下文，切换不能覆盖全局 DPI / 显卡选择。

全局设备状态通过严格 devices 快照传递，只含串口/盒子、能力、测试和 GPU 的显式白名单；不得为支持无活动工作区而放宽整份 state 的来源检查。切换失败保持资格撤销，用户从侧栏重新选择游戏才重新尝试；同 ID 重载也需要新的 epoch。

异步流程必须保留来源：

- 文件对话框结束后先确认开始时工作区仍有效，再提交导入/导出。
- 模型删除确认、拟合完成与算法读取不能落到另一个工作区。
- effect 的清理命令使用挂载时上下文；旧页面卸载不得停止或隐藏新工作区的采集/画布。
- 原生表面大小相同也要在新 epoch 补发，不能只依赖 ResizeObserver。
- 不能从一个工作区的 UI 状态复制输出资格、目标身份或模型启用状态。

同一游戏内的目标缺帧和侧键行为不应被这套工作区隔离顺便改写。

## 5. 全局界面和本地化

保留 DIMO 外壳、语义 CSS 变量、离线字体、浅深色和中文/英文。新文案加入独立的 i18n 词典，并由 i18n/index.ts 合并；原生机器状态码先映射成人能理解的文字，不直接作为用户标签。

全局设置继续只管理常规、固件、输入设备、显卡与数据。数据源、游戏灵敏度、校准和算法说明留在当前游戏设置；公共采样/模型文件保留来源与兼容元信息，启用关系属于工作区。

页面上下文栏按当前页面选事实；故障优先、恢复撤销与去重保持。消息身份要区分 epoch，不能让上个游戏的故障或轮播游标污染新游戏。日志可以全局保留，但应有工作区来源和范围筛选。

## 6. 后台验收

至少覆盖：

1. 新游戏目录状态与真实能力一致，未接入游戏不能运行。
2. 旧 PUBG 配置、校准、模型、采样和自定义数值完整保留。
3. 创建不切换、不自动启用模型；同名配置用不同稳定 ID 隔离。
4. 切换时清目标、旧场景、原生翻译源和表单；保留全局设备状态。
5. 旧/缺失上下文事件、旧异步文件流程、旧绘制 cleanup 被阻止。
6. 算法面板、绘制表面和采集在新上下文恢复；不增加逐帧 Web 流。
7. 当前功能的中文/英文、主题、键盘导航和错误反馈完整。
8. 类型、lint、架构检查、组件测试和生产构建通过。

后台命令：

```text
pnpm typecheck
pnpm lint
pnpm test
pnpm build:ui
pnpm check:architecture
```

合成数据和组件测试不能作为实际游戏、真实 1000Hz 输入或跨屏 DirectX 验收。前台自动操作、真实输入和新的设备烧录继续遵守用户授权范围。


工作区 values 使用 PUBG / CS2 两套严格 schema；bootstrap 及原生客户端再次核对 gameId，禁止混用或混合参数。公共配置输入只提交命令，源帧、骨点与 GPU 像素不进入 Web。GameUiModule 的 OverviewDetails / EspSettings 为可选专用组合点；不能在公共页面堆叠游戏算法分支。
