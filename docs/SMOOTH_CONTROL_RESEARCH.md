# 公开快速平滑控制方案比较

调研日期2026-10-13；用户自行测试期间阅读公开源码和原始资料，没有安装或执行外部程序。随后按用户要求加入部位选择、实时FOV换算和按住锁定恢复。公开代码存在不等于已证明某个FPS中的锁定时间。

### 贝塞尔名称不保证平滑速度

Aimmy这份实现的两个控制点分别取起终点连线的1/3、2/3。[MovementPaths源码](https://github.com/Babyhamsta/Aimmy/blob/28211a569ccb4e012a46e8aed54d9b812d5075bd/Aimmy2/InputLogic/MovementPaths.cs)使用标准三次公式。由代数推导，忽略整数舍入时这种配置退化为直线插值；这属于本次推断。它没有自动定义跨时间的起步、刹车或移动目标更新规律。因此替换为“贝塞尔”名称不能单独解决三秒拖尾或反馈延迟。

### 延迟不能靠增益无限提高来解决

[MathWorks Smith Predictor示例](https://www.mathworks.com/help/control/ug/control-of-processes-with-long-dead-time-the-smith-predictor.html)演示内部响应模型与实际反馈校正的组合，也讨论模型/延迟误差带来的不稳定。这支持先估计已发出的效果、再让真实反馈纠正的方向，不证明本项目已具备完整Smith控制器。PC0.5.2目前是有界位移效果/反馈相位估算，仍需真实延迟变化与物理输入测试。

### 人体学习的边界

[鼠标点选LQR原研究](https://arxiv.org/abs/2002.11596)用距离与动作jerk等代价拟合点选行为；其任务是鼠标指针点选。它支持研究速度和起停的控制代价，但不证明学习用户瞄准路线是FPS跟随的行业标准。当前只学习用户速度/起停上限的边界继续保留。

## 适合Reader链路的后续路线

以下保留0.5.4调研候选；0.5.5已落地有限目标速度估计与本地Ruckig状态轨迹，未实施完整观测滤波：

1. 对核验后的目标坐标/角速度使用速度适应滤波，按真实Reader源采样间隔更新，不把控制循环重复采样算作新观测。
2. 分离目标自身运动与本机视点转动，估算短期目标速度并加入有限前馈。不能直接用总误差差分当人物速度，否则自己的输出和后坐力也会被误当作目标移动。
3. 在当前速度/加速/刹车约束基础上比较jerk受限规划，优先快速接近、按剩余距离及时刹车。参数仍受串口与整数计数能力限制。
4. 以实际反馈持续纠偏；保留稳定区、接近时噪声归零、松键停止和不积压旧指令。

评估应使用同一Reader录制场景比较0.06°稳定区时间、移动目标滞后、过冲次数与停止延迟，再由用户现场测试。没有必要仅因公开源码用了PID就增加积分；也不应以随机噪声掩盖控制误差。

Ruckig的Tracking接口属于Pro，Community中间路径点可能走云端，不能将其误称免费的本地跟踪组件。0.5.4阶段只参考方法。0.5.5已固定引入Ruckig v0.15.3 MIT核心，静态编入mousebox-core，仅调用本地状态到状态接口；不包含云端、Python或Pro Tracking。

## 实时FOV与鼠标输入换算

用户提供DPI和游戏各项灵敏度，FOV由Reader实时提供。项目世界角度计算已经使用实时视点且不依赖固定FOV，预览使用实时FOV投影。剩余困难是游戏如何将计数转成角度，不能仅由透视投影推导。

[Epic官方UInputSettings](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UInputSettings?lang=en-US)定义可选FOV鼠标缩放；这不证明PUBG当前实例的具体开关或完整公式。用户指出公开方案不要求逐FOV实测后，调整设计：精确匹配是原实现的保守限制，不是连续反馈控制的必要条件。上文Aimmy直接按目标屏幕误差修正，NeuralBot按误差反馈并配置灵敏度与速度，没有要求每个FOV分别标定；仍需要适当参数，源码也不构成速度性能证明。

PC0.5.4默认采用明确标注的输入响应估算：`yaw/count = 0.002 × 10^(S/50) × 2.5 × FOV/90`，pitch按垂直倍率和反转方向确定。S使用操作者所选常规/瞄准/当前镜倍开镜灵敏度；FOV取Reader当前View。物理DPI用于速度学习单位换算，不再次乘入已经是HID计数的程序位移。

指数滑条转换可在作者公开的[历史实现](https://gist.github.com/Youngv/0a86edde6110e793333ff2330065aab1)中核实；另一个[灵敏度转换器源码](https://github.com/kamilanta/gta_sensitivity/blob/main/sensitivity%20code)同样使用指数转换和线性FOV调整，但给FPP/TPP不同常数。这些是作者实现，不是当前PUBG官方函数。2.5/90整体响应模型是本项目的工作假设：S50、FOV80/90分别约0.044444/0.05°每计数，与已有本地测量接近。只读游戏配置得到Scoping菜单59.927795、LastConvertedSensitivity0.031589、垂直1、未反转；支持指数转换的近似，但不证明所有输入模式、镜倍或变焦响应均已核验。不会用该读取更改游戏设置或触发输入。

估算不写入实测校准表；旧测量原样保留，可选“仅匹配实测FOV”。正常变焦只更新系数，不改按住的配置代次；参数/模式修改仍终止旧控制。窄FOV下稳定区按`min(1,FOV/80)`收紧，不让固定角死区遮住可见偏差。Reader目前没有核验的当前瞄准模式/镜倍灵敏度信号，不能只根据FOV自动猜模式；当前界面明确要求选择正在使用的灵敏度，独立镜倍填对应值。

离线连续FOV90→30→120、35ms采样/80ms延迟、真实响应为估算0.8/1/1.2倍时持续跟随并收敛，末段没有持续位移；另测FOV2.5/15/45/140/179的静止收敛。结果不等于全部镜倍实测，更不保证任意角差或FOV都在0.4秒内完成。无需新远程模块、该结论属于0.5.4验证范围；0.5.5新库与验证见下文。

## PC0.5.5：公开曲线实际落地

用户认为当前路线人机、接近时突然拖慢、近处目标跟随慢。没有找到可证实的“FPS公认最佳曲线”结论；原始人体最小jerk研究针对平面到点动作，不是竞技FPS排名。Ruckig的公开原论文和本地计算核心能够从当前运动状态规划限速度/加速度/jerk的最短可行状态轨迹，适合改善起停；这仍不是人类轨迹证明。

采用[Ruckig v0.15.3固定源码](https://github.com/pantor/ruckig/tree/37b6e7a4c60f5befd2506741d5f7d0ae7eefb3db)，原MIT许可、归档和源码哈希见third_party/ruckig。PC用Position接口，按两个轴当前速度/加速度、剩余计数和有界目标速度重规划；不执行固定终点的长贝塞尔flick，不将其当完整Pro Tracking。求解单位缩放为1000计数，修正未缩放大数值重规划的一次数值拒绝。

用核验Living点的源内时间差估计世界运动，2–150ms间隔有效，同点立即零速度；角速度<1°/s不做前馈，目标端速度≤档位90%，本地年龄≤35ms+25ms规划前瞻。物理距离本身不降低速度；相同横移速度下近处角速度更大。没有源时钟与本机时钟相减，也不宣称提前知道人物下一帧。

五档新上限是600/800/1600/2400/3200counts/s，已部署v4只接受±4；因此新后三档须配套v5扩展能力。PC没有通过更高串口频率换速度，仍最多200对/秒。量化/停止/资格失效可打断数学连续轨迹，不保证原始HID整数点的jerk连续。对误差响应0.75–1.25范围允许双轴一致的有界前缀近似用于估算相位，仍非接受回执；零相机变化绝不启动相位。验证及边界见CONTROL_RESPONSE.md。
