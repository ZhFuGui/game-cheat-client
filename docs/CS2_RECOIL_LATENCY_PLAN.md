# CS2 实际后坐抵消：延迟与运动滞后优化方案

PC2.2.5后续决定：用户改为手动游戏体验反馈，要求直接提供版本对比。本轮不实施B阶段分段计时；保留v1并新增v2快速通道，实际实现与边界见[算法版本](AIMBOT_VERSIONS.md)。下文保留PC2.2.4当时的分析与计划范围。

2026-10-24，PC2.2.4。范围是现有 CS2 控制器；PUBG 控制、Reader 协议、固件与用户参数不变。先修复已证实的误暂停，再测真实闭环，最后决定运动结构及参数。本文未实施新的后坐倍率、平滑参数或前馈算法。

## 1. 已经有证据的问题

### 1.1 短暂停止被变成永久松键门控

PC2.2.3 将相同原生选择器下的 simulation 时间回退视为时钟故障，并撤销本次按住。随后状态被覆盖成 `release-then-hold`，必须重新按键才能继续。

本轮正式 Reader 13202/60Hz 的只读记录，12 秒中有 720 个不同观测。`#171921 → #171922` 在相同 worldGroup/nativeContext 下，从 `4247543.802419186` 回到 `4247543.0`，约回退 12.54ms。Reader 已核验：853690/940fd0 会因预测路线选择 Controller 或世界时间，simulation **不承诺跨批严格单调**；采集序号与 QPC 才是另一个层面的时序依据。

2.2.4 删除这项错误的跨批模拟时间假设，仍完整核验每一批 P/U、游戏时间、眼角来源、采集序号和 QPC。暂时缺组、采集乱序、调度中断不再丢弃锁定身份；恢复当前可信数据后继续同一对象。没有沿用旧角度或旧坐标输出。

### 1.2 无响应检测使用了不同处理阶段的角度

旧看门狗检查 `Local.input_view_angles / dwViewAngles` 是否改变，而普通本地 source2 的瞄准基准实际来自受控 Pawn.v_angle。Reader 没有证明两者每帧相同或处于相同输入处理阶段。

2.2.4 的响应观察优先使用已核验的普通本地 Pawn 预测输入角，其次是当前 Pawn 输入角，最后才是全局输入角；来源在页面显示。这里仅修正响应观察，不叠加任何后坐补偿。

真正长时间没有输入角响应时仍停止发位移，但保留锁定身份，等待新的实际输入角变化；不靠周期试探移动恢复。侧键短暂失去回传时立即停止，只在现有设备松开计数证明没有真实松键、且回传重新新鲜后恢复。真实松键、明确死亡、换人物/进程/世界或会话撤销仍结束本次意图。

## 2. 目前延迟到底测到了什么

本轮没有注入鼠标或操作游戏。对正式 60Hz 来源进行了两段后台只读观察：

| 观测口径 | 数量 | 年龄中位数 | P95 | P99 |
|---|---:|---:|---:|---:|
| 每个新帧第一次被 IPC 探针看到 | 720 个不同帧 | 7.86ms | 11.99ms | 16.97ms |
| 约4ms轮询，包含同一帧停留期间的重复观察 | 2025 次、720 个不同帧 | 11.95ms | 19.95ms | 22.21ms |

这些年龄来自当前读取区间中点的时钟映射。第一种口径偏向到达时刻；第二种更接近帧在控制循环中停留时的年龄，但仍不是原生每 tick 的精确分布。它们包含只读 IPC 观察开销，不能称作端到端执行延迟。第一段时钟/读取不确定度中位3.34ms、P95 8.10ms；不能把年龄的小数位当成微秒级真值。

需要分别识别以下时间：

```text
Reader 读取区间 [t_read_start, t_read_finish]
  → 原生收到并发布 t_publish
  → 求解及提议 t_solve / t_propose
  → 串口接受 t_accept
  → 写调用开始/完成 t_write_begin / t_write_end
  → 盒子与 USB HID 处理（目前没有逐条完成 ACK）
  → 游戏消费并改变受控 Pawn 输入角
  → 下一次 Reader 读取区间首次包含变化
```

当前已知边界：

- 用户的 `responseMs=20` 是手动模型假设，既用于状态外推，也用于待反映位移账本核销；**没有被测成20ms**。
- 60Hz 的周期16.67ms。若输入事件相位均匀、采样瞬时，等下一次采样的理论平均约8.33ms；真实读取区间、系统调度与发布还要单独计入，不能再与已测年龄机械相加。
- 当前v7链路已握手500000 baud。每次有限步的START+MOTION共48字节，8N1的纯线路串行化下限为0.96ms；写调用完成不表示HID或游戏已消费。
- 设备最小间隔2ms、单轴100计数、XY预算200均来自能力协商；它们是能力上限，不是实测延迟。USB、TTL驱动和游戏输入阶段的额外时间仍未测。
- 当前 `tryOneShot()` 在串口工作线程忙时拒绝；`reject()` 会清空运动速度与小数状态。需要统计实际拒绝率及其原因，才能判断它是否额外打断追赶，不能仅凭源码推断现场一定频繁发生。

只读证据在 `R:/cs2/validation/cs2-hold-recovery-20261024/`：`read-only-latency.json`、`latency-summary.json`、`read-only-control-age.json`、`control-age-summary.json`。

## 3. 现有平滑为什么可能拖住后坐补偿

当前求解为：

```text
h = sourceAge + responseModel
shotOffset = E(P, simulation+h) + E(U, simulation+h)
error = desiredTargetAngle - verifiedEyeBasis - shotOffset
remainingError = error - commandsExpectedNotYetVisibleInSample
counts = signedDerivativeInverse(remainingError)
velocity → 比例追赶 / 速度上限 / 加减速 / 停止距离 / 可选学习模型
step → 小数余量 / 当前设备每步和XY预算限制
```

目标转移误差与后坐抵消误差经过**同一运动通道**。即使后坐量求值正确，也要经过追赶与加减速；不能因为数据齐就认为补偿瞬时生效。

用户当前速度ID3对应75%链路上限，比例增益60/s。忽略延迟、量化和所有限幅时，连续小信号近似时间常数 `1/60≈16.7ms`，完成90%阶跃约 `ln(10)/60≈38.4ms`。这是源码的线性近似，不是设备实测。以当前导数0.0275°/计数为例，2°约73计数，虽然能容纳在单轴100计数里，现有平滑仍会分多步追赶。

### 真实控制器的离线阶跃实验

`tests/native/cs2_motion_benchmark.cpp` 直接运行生产 `OutputProgram`，没有另写一个简化控制器。条件：2°静态角阶跃、速度ID3、1:1公式、导数±0.0275、2ms/100/200设备能力、4ms假定读取发布延迟、固定20ms响应模型、1ms仿真步。P/U为零，用共用的角误差通道隔离运动滞后，**不是枪械后坐波形或实机压枪测试**。所有案例都没有改变20ms去迎合假定物理延迟。

| 假定物理响应延迟，60Hz | 第一次达到90% | 最终持续在±0.1°内的起点 | 最大过冲 |
|---:|---:|---:|---:|
| 0ms | 98ms | 138ms | 0° |
| 10ms | 77ms | 115ms | 0° |
| 20ms | 59ms | 71ms | 0° |
| 50ms | 89ms | 723ms | 1.30° |
| 100ms | 139ms | 3秒内未稳定 | 16.97° |

0ms按1ms仿真步最早下一步生效，不能解释成真正无时间传递。90%只表示第一次穿过阈值，不代表已经稳定。100ms案例出现振荡和越界暂停，不能只取139ms宣称快速收敛。

20ms模型与假定20ms物理延迟相符时，30/60/120Hz三个案例的90%时间均59ms。此结果只说明这个阶跃案例受运动/账本模型主导，**不证明提高频率没有价值**。50ms物理延迟却按20ms核销时，账本过早认为动作已被采样反映，容易追加纠正并产生过冲；反向误差也可能让实际更快的链路被过度等待。结论是先核实响应模型及平滑结构，不能盲目加频率或速度。

Debug/Release分别导出 `motion-benchmark-debug.json` / `motion-benchmark-release.json`；15个案例完整保留，包括不稳定结果。复现：设置环境变量 `MOUSEBOX_CS2_MOTION_BENCHMARK_OUTPUT` 为报告绝对路径，再运行 `mousebox-tests --suite cs2`。只使用合成设备。

## 4. 优化实施顺序

### A. 修正误暂停和保留锁定——本轮实现

消除错误的跨批模拟时间门禁、修正响应观察来源，临时故障恢复同一人。页面显示锁定身份、当前暂停和最近一次原因/次数；恢复时撤销当前警告。真实无响应停止输出并等待实际恢复，保持来源/侧键/会话最终复核。

不改P/U求值器、倍率、衰减、积分、20ms、增益、速度比例、加减速、年龄上限或学习模型。先把间断因素从效果问题里分离。

### B. 加原生分阶段计时，确认真实响应——下一阶段

1. 在原生记录上述时间点及来源capture、提议ID、实际接受/拒绝原因、有限位移和受控Pawn输入角；采用预分配有界环形缓冲，离开实时线程后才导出，不逐包经JS或同步写盘。
2. 区分“因来源修订变化而拒绝”“串口忙而拒绝”“已接受后被STOP撤销”“写出完成”“采样观察到变化”。接受与写调用完成都不能伪称物理ACK。
3. 先录用户正常操作，统计 source-age、求解/排队/写调用的P50/P95/P99、拒绝比例、暂停次数及持续时长。自动统计必须剔除跨身份、失效帧和窗口边界。
4. 若正常操作无法区分手动鼠标与控制输出，再请用户配合一轮保持物理鼠标静止的有限小角测试，不自动启动校准或注入。首次看到变化只能给出被读取区间和采样频率限制的响应区间，不能得到精确单包游戏执行时间。
5. 用同一段数据比较当前20ms模型与实际响应区间，不同时调平滑、频率和增益。模型稳定前，不实现自动学习一个看似精确的延迟值。

### C. 根据测量调整两处结构，不先调大参数

**提议与提交分离**：提议不应在串口拒绝后丢掉整个已接受运动状态。拟拆成可提交候选状态：成功接受才记入账本，失败只撤回本次提议；STOP/身份变化仍彻底清理。先复现实际拒绝场景，再用相同输入回放对照，不能丢弃必要的最终来源复核来提高“成功率”。

**目标追踪与后坐扰动响应分开**：慢速/学习模型继续决定大角度追踪；已验证的后坐变化可使用独立、受同一设备约束的快速补偿通道。保持同一个E(P/U)物理定义，不再乘倍率。更强抗扰与柔和目标切换应作为不同目标设计；这与控制理论中将参考跟踪和扰动抑制分别设计的思路一致。[MathWorks：双自由度控制器](https://www.mathworks.com/help/control/ug/two-degree-of-freedom-2-dof-pid-controllers.html)

首个候选仅对**已收到**的后坐变化做增量前馈，反馈校正剩余残差。例如在可信连续游戏时间锚点上，将上一批已知P/U先推进到当前批时间，再比较当前实测求值，得到新变化估计；遇预测路线不连续、时间锚点不可靠、缺组或身份变化就重建基线，不能把时间路线切换当作新冲量。

```text
Δobserved = currentRecoil(nowAnchor) - previousKnownRecoilAdvancedTo(nowAnchor)
feedforwardAngle = -Δobserved
candidate = constrainedFeedforward + smoothResidualTracking
```

此式是待验证的设计，不是已上线算法。必须解决以下细节才能启用：

- 前馈按唯一有效观测更新，不按500Hz重复同一帧；缺帧不累计未知冲量。
- 前馈与平滑反馈合用一个**已接受**账本。其预计影响从反馈剩余误差中扣除一次，避免绝对误差已含P/U，又额外重复抵消变化。
- 逐轴符号、横纵导数、小数余量、单步/间隔/XY预算与人类停止资格统一；限幅后保留的残差有界，不能出现松键后的积分或迟到补偿。
- 时间路由发生不连续时只能用当前完整绝对解恢复，不能跨路由求差；不能只比较context编号来证明连续。
- 不预言未收到的新射击、受击或随机散布；不将相机反馈、view-punch、准星动画再次叠加进子弹方向。

延迟补偿必须有可验证的对象模型与延迟估计。Smith predictor的官方示例同样明确要求这两者，并说明盲目加大增益可能增大过冲或失稳；本项目不能直接照搬其化工对象参数或宣称已有完整Smith predictor。[MathWorks：延迟与模型要求](https://www.mathworks.com/help/control/ug/control-of-processes-with-long-dead-time-the-smith-predictor.html)

### D. 同条件比较后再决定是否上线

保持同武器、距离、灵敏度、开镜、目标运动、速度ID和Reader频率；对照修复后的现状、延迟模型修正、提交状态修正、最后才是独立抗扰通道。一次只改变一项。

指标包括：当前可求值发射方向与所需角的残余Pitch/Yaw RMS/P95、首个有效纠正时间、T50/T90、稳定时间、过冲/反向次数、拒绝率、暂停持续时间和缺帧恢复同人成功率。残余角不是实际落点误差，缺少开火子时刻和散布时不能冒称测得每枪命中偏差。人物移动和手动输入需单独标注，不能混成控制器自身误差。

只有在残余误差/响应改善，同时过冲、抖动、暂停和设备约束没有恶化时保留候选。先输出完整曲线和坏案例，再决定参数；没有实机对照前不承诺优于常见公开压枪方案。

## 5. 当前不缺字段，而缺测量证据

现有正式字段足以修正误暂停、观察当前Pawn响应、完成上述计时设计和控制器离线对照。本方案不要求Reader新增字段，也不以新字段作为继续工作的前提。盒子逐包完成ACK、真实游戏消费时刻、未知未来冲量和逐枪散布仍不可观察，需要明确保留这些不确定性，不能用20ms或一次采样时间伪装成实测事实。
